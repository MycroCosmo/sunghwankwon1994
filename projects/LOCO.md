# LOCO | 장소 공유 서비스의 설계와 검증

소스는 비공개 저장소에서 관리합니다. 이 문서는 공개 가능한 설계 요약이며, 기본 브랜치와 별도 개선 브랜치의 결과를 구분합니다.

## 프로젝트 개요

기존 React·Spring Boot/JPA 프로젝트 이후 Flutter·NestJS·PostgreSQL/Prisma로 개인 재구현했습니다. 지도방, 장소, 리뷰, 인증·권한과 지도 조회 전략을 다룹니다.

## 1. 리프레시 토큰의 일회 소비

기본 브랜치에서 토큰은 원문 대신 해시로 저장합니다. 재발급 시 유효 상태를 조회한 뒤 다음 조건에 해당하는 토큰만 폐기합니다.

```text
WHERE id = ? AND revokedAt IS NULL
```

갱신 건수가 1인 요청만 다음 리프레시 토큰을 저장합니다. 기존 토큰 폐기와 새 토큰 저장을 하나의 DB 트랜잭션으로 묶었습니다.

```text
동일 토큰으로 요청 A, B
  A: 조건부 UPDATE 성공 → 새 토큰 저장
  B: 이미 폐기된 행 → 갱신 0건 → 재발급 거부
```

개선 브랜치의 PostgreSQL API 테스트에서는 두 재발급 요청을 동시에 보내 `201`과 `401`이 각각 한 번 반환되고 활성 토큰이 한 개 남는 것을 확인했습니다. 이 검증은 해당 동시 재발급 시나리오의 결과이며 모든 계정 상태 변경 경쟁 조건을 검증했다는 뜻은 아닙니다.

## 2. 탈퇴 후 기존 인증 정보 처리 — 별도 개선

기존 코드는 탈퇴 상태를 기록하고 이후 로그인·재발급에서 검사했지만, 이미 발급된 액세스 토큰의 요청에서는 사용자 상태를 확인하지 않았습니다.

개선 브랜치에서는 JWT 서명·만료 검증 뒤 DB에서 현재 사용자를 조회해 삭제되었거나 존재하지 않는 계정을 거부합니다. 탈퇴 처리에서는 다음 변경을 하나의 Prisma 트랜잭션으로 실행합니다.

```text
사용자 deletedAt 기록 + FCM 토큰 해제
  → 활성 리프레시 토큰 폐기
  → 미사용 비밀번호 재설정 토큰 사용 처리
  → 모두 성공하면 커밋, 중간 오류가 나면 롤백
```

실제 PostgreSQL과 Nest API를 사용해 아래를 확인했습니다.

| 테스트 | 확인 결과 |
| --- | --- |
| 탈퇴 전 발급받은 액세스 토큰으로 내 정보 조회 | 탈퇴 후 401 |
| 탈퇴 전 리프레시 토큰으로 재발급 | 401, 활성 토큰 0개 |
| DB 트리거로 토큰 폐기 실패를 주입 | 요청 500, 사용자 탈퇴 상태와 토큰 변경 롤백 |

이미 인증을 통과한 실행 중 요청을 취소하거나, 비밀번호 변경·로그아웃 시 모든 액세스 토큰을 즉시 폐기하는 세션 버전 기능은 이번 변경에 포함하지 않았습니다.

## 3. 공개 여부와 수정 권한 구분

지도방의 공개·비공개 상태와 방장·멤버·작성자의 권한을 별도로 검사합니다. 현재 공개 지도방 API도 인증이 필요합니다. 공개라는 명칭을 익명 접근 허용으로 해석하지 않습니다.

| 동작 | 코드에서 구분하는 조건 |
| --- | --- |
| 비공개 지도방 조회 | 방장 또는 멤버 |
| 장소 추가 | 지도방 가입 및 정책 검사 |
| 장소 수정 | 작성자 |
| 지도방 수정·삭제 | 방장 |
| 비공개방 가입 | 초대 코드 |

## 4. 장소 목록과 지도 마커 조회 분리

목록은 검색·태그·정렬과 커서 기반 페이지 처리를 사용합니다. 페이지의 장소들에 대한 리뷰 통계는 묶어서 조회해 응답에 결합합니다.

지도 마커는 현재 보이는 영역과 확대 수준을 기준으로 조회합니다. 장소가 많은 범위에서는 여러 정밀도의 `PlaceMarkerCell`을 이용한 집계 응답을 사용합니다. 이 문서에는 별도로 측정하지 않은 처리량이나 응답 시간 개선 수치를 넣지 않았습니다.

## 5. 이미지와 DB의 실패 처리

지도 커버·프로필 이미지 교체는 새 파일 저장 후 DB를 갱신하고, DB 갱신 실패 시 새 파일 삭제를 시도합니다. 기존 파일은 DB 갱신 성공 후 삭제합니다.

파일 삭제 함수는 오류를 삼키는 최선 노력 방식입니다. 따라서 삭제를 시도한다는 것과 고아 파일이 절대로 남지 않는다는 것은 다릅니다. 지속적인 재시도·고아 파일 정리까지 보장하는 구조는 아닙니다.

## 데이터 제약

지도방 멤버 `(mapId, userId)`, 리뷰 `(placeId, userId)`, 즐겨찾기 `(userId, mapId)`에 고유 제약을 사용합니다. 리프레시 토큰 해시와 초대 코드에도 고유 제약이 있습니다.
